argument-hint: "<file or directory to audit>"

Audit code using a clean-room process: $ARGUMENTS

## Workflow

### 1. Identify files and confirm scope

Parse `$ARGUMENTS` for file paths or a directory. If a directory, list the code files in it. Read each file to confirm it contains auditable logic. Skip configuration, boilerplate, and files with no domain rules.

Identify every external input the code-under-audit depends on: parameter files, configuration files, lookup tables, data files generated by another process or agent. These are **out-of-scope dependencies**. The audit cannot verify their accuracy because the builder will take them as given rather than recreating them.

Present the user with:
- The list of files in scope for the audit (the code that will be documented, rebuilt, and compared).
- The list of out-of-scope dependencies and what each one provides.
- A note that the audit guarantees apply only to in-scope code. Any error in an out-of-scope dependency will propagate through the rebuild the same way it propagates through the original.

Wait for the user to confirm or adjust the scope before continuing. The user may move files between the two lists or add files not initially identified.

### 2. Prepare scratch directory

Create `.scratch/clean-room/` in the project root that contains the code-under-audit. This holds the specification and rebuilt code. Create `.scratch/clean-room/build/` for the builder's output.

### 3. Launch the documenter

Spawn a `documenter` agent. In its prompt, list every in-scope file by full path and tell it to write the specification to `.scratch/clean-room/spec.md`. Also list the out-of-scope dependencies and instruct the documenter to describe them as external inputs (format, content, and how the code uses them) without documenting their internal logic.

Wait for the documenter to finish.

### 4. Review the specification with the user

Read `.scratch/clean-room/spec.md`. Confirm the specification covers every in-scope file and contains no verbatim code.

Present the specification to the user. Ask the user to confirm:
- The specification accurately describes what the code is supposed to do.
- The domain rules, formulas, and transformations are correct as described.
- Nothing material is missing.

Do not launch the builder until the user confirms. If the user identifies errors or omissions, either correct the specification directly or relaunch the documenter with the user's feedback.

Record every change the user makes to the specification. These are places where the user's understanding of the intended behavior diverges from what the documenter observed in the code. Save these as **user-specification divergences** for the final report.

### 5. Gather project context for the builder

Before launching the builder, collect:
- The programming language.
- Available libraries and their versions, from the project's dependency files (e.g. `renv.lock`, `requirements.txt`, `package.json`).
- The file names the builder should create (matching the original in-scope file names).

### 6. Launch the builder

Read `.scratch/clean-room/spec.md`. Spawn a fresh `builder` agent (not a fork — the builder must not inherit conversation context containing the original code). In its prompt, include:
- The full text of the specification.
- The programming language, libraries, and file names from step 5.
- The output directory: `.scratch/clean-room/build/`.
- The out-of-scope dependencies: their file paths and formats, so the builder can reference them as inputs without recreating them.

Do not include any code from the original files in the builder's prompt.

Wait for the builder to finish. Read the rebuilt files from `.scratch/clean-room/build/`.

### 7. Compare

Read the original files and the rebuilt files. For each pair, identify substantive discrepancies — differences in domain logic, formulas, data transformations, edge-case handling, or control flow. Ignore cosmetic differences: naming, style, comment placement, import order.

Classify each discrepancy as one of:

- **Undocumented logic.** The original contains logic the specification did not capture and the rebuild does not have. Could be intentional but unclear, or vestigial code that should have been removed.
- **Missing implementation.** The specification describes a rule the original does not implement. The builder followed the spec; the original skipped it. Possible bug in the original.
- **Formula mismatch.** Both implement the same rule but use different expressions. Check whether they produce the same result for all inputs. If they diverge for any input, describe when.
- **Edge-case divergence.** The two handle a boundary condition differently, or one handles it and the other does not.

### 8. Report

Present each discrepancy with:
- The file and domain rule involved.
- What the original does.
- What the rebuild does.
- Why the difference matters, or a note that it may not.

If the user changed the specification in step 4, include a separate section listing each user-specification divergence: what the documenter originally wrote (reflecting the code's actual behavior), what the user changed it to (reflecting the user's intended behavior), and which in-scope files are affected. These are places where the code does not match the user's intent and may contain bugs the clean-room comparison alone would not catch, because the builder worked from the corrected specification.

Restate the out-of-scope dependencies at the end of the report and note that the audit did not verify their contents.

If there are no substantive discrepancies and no user-specification divergences, say so.
